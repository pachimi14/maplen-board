### 1.1 依頼文に無い、設計に影響する実測4点

**(1) `enhance-price/latest`(現在価格)は自宅PCからも 403。** history は自宅PCから **200**(32時間窓で約4.4KB)なのに、latest は PC からも **403**(430,447 B の同じメンテHTML。`period=0` 付き・`Accept` ヘッダ付きでも同じ)。
∴ 現在価格の非表示は「方針」ではなく**ほかに選択肢がない**。そして **maplenEnhancebot 自身の `fetch_starforce_prices` も今は動かない** — `main.py` の `API_BASE` がこの latest と同一URLなので、そちらの強化費は既に「登録時点の値」しか出せない状態。§5 の差し替え要望は、好みの問題ではなく**現在壊れているものの修復**にあたる。

**(2) `update.py` は接続レベルの失敗で run 全体がクラッシュする。** VPS の失敗は 403 ではなく
`requests.exceptions.ConnectionError: ('Connection aborted.', ConnectionResetError(104, 'Connection reset by peer'))` で、**未処理例外のまま exit 1**。
`fetcher.get` は 429 しか扱わないので、403 のように `comboErrors` へ数えて次の組へ進む経路に**乗らない**。
4時間ごとなら「次の run で拾う」で済んだが、**1日1回にすると「1本の接続リセットで翌日まで欠測」**になる。頻度を落とす判断とセットで、ここは直す必要がある(計画書の論点)。

**(3) `avg_price` は「取引の平均」で、取引が無い時間は 0。** 実測(item 1152108 ☆10, 2026-11-18T14:00Z): `sum_enhance_count=0` の行は `avg_price = max_price = min_price = 0.0` で、生きているのは `end_price` だけ。
∴ **24時間平均は必ず `end_price` から計算する**。`avg_price` を平均すると 0 が混ざって激しく過小になる。

**(4) 1日分の増分は gzip 235 KiB。** 1 UTC 日(2026-11-17)の hourly 行は SF 17,664 + CUBE 3,264 = **20,928行**、CSV **1,392,849 B(1.33 MiB)** → **gzip 240,966 B(235.3 KiB)**(JSON でもほぼ同じ 237.4 KiB)。
DB 丸ごとは 903.7 MiB。∴ **転送は増分で決まり**(§4(b) は実測で結論が出た)。

## 2. §5 の3点への回答

### 2-1. 軽い口を足すか → **足す。推奨する。**

実測した現状のコスト:

| 口 | 1装備あたり | 1キャラ(十数装備)換算 |
|---|---|---|
| `GET /sf-history/prices?itemId=` | **228,868 B** | **約3.0〜3.4 MB** |
| `GET /sf-history/cube-prices?itemId=` | **82,174 B** | 約1.1 MB |

必要なのは末尾の1点(+24時間平均)だけなので、**99%以上が無駄**。
対して「全34装備 × 22星 × (最新 + 24h平均) + キューブ4種」は数値 1,800 個程度で、**1本 20〜30 KB** に収まる。**2桁の削減**で、しかも装備数ぶんのリクエストが 1 本になる。

**条件(そちらにも影響する規約)**: 応答キーの単一の正は `server/sf-history/contract/response_fields.json` で、
`server/sf-history/tests/test_response_contract.py`(実応答のキー集合を突き合わせ。余分なキーも欠けたキーも落ちる)と
`exp_ranking/web/src/sfhistory/integrations/contract.test.js`(web 側の正規化が全フィールドを保つか)が両側から縛っている。
∴ 新しい口は **このファイルに先に足してから**両側を通す。形を後から黙って変えることはできない(できないのが利点)。

**レスポンスの形(たたき台。確定は計画書で、ユーザー承認後)**:

```
GET /sf-history/latest-costs            # 全装備まとめて1本
{
  "generatedAt": "2026-11-25T08:05:00Z",   # この応答を作った時刻
  "dataAsOf":    "2026-11-25T08:00:00Z",   # 1時間足の最後の点(= データの鮮度)
  "updateCadence": "daily",                 # 復帰後に "4h" へ戻る
  "interval": "1h",
  "upgradeCount": 22,
  "cubeOrder": ["RED","BLACK","ADDITIONAL","WHITE_ADDITIONAL"],
  "items": [
    { "itemId": 1003720,
      "aliasItemIds": [1003719, 1003720],
      "maxStar": 22,
      "starLatest":  [ ...22個, null可 ],   # end_price の最終点
      "starAvg24h":  [ ...22個, null可 ],   # 直近24時間の end_price 平均
      "cubeLatest":  [ ...4個,  null可 ],
      "cubeAvg24h":  [ ...4個,  null可 ],
      "pointsUsed24h": 24                   # 平均に使った点数(欠測の正直な開示)
    }, ...
  ]
}
```

方針として入れてあるもの: ①**最新と24h平均を両方返す**(§2-3 の最悪ケース31%のため、呼び出し側が乖離を見られるように) ②`aliasItemIds` を同梱(そちらの「着けている itemId から価格グループを引く」用。34装備すべてに入っている) ③`dataAsOf` で鮮度を明示(「強化費は MM/DD HH:mm 時点」の表示用) ④`pointsUsed24h` で欠測を隠さない ⑤**単位変換はしない**(§2-2)。

### 2-2. 価格の単位 → **同じ。`price_divisor` を二重に適用してはいけない。**

- sf-history 側: `db.py` は API の `endPrice` を **無変換**で保存(コード内コメントも "taken from the API's `endPrice` unconverted")。history の生値は最初から小数。
  実測(item 1003720 ☆10、本日 PC から直叩き): `endPrice` = `304497.522525` / `301358.372808` / `298219.223092`。
- maplenEnhancebot 側: `parse_starforce_prices_from_enhance_data` が `starForce[].closePrice` に `convert_price(raw, divisor) = int(raw)/divisor` を適用。`config.json` の `price_divisor` は **1000000000000000000**(既定どおり)。

**1点突き合わせ**: latest が 403 で生の `closePrice` を今は取れないため、そちらの `data/cost_cache.sqlite` の
`planner_enhance_price.payload_json` に残っていたキャッシュ(item **1152108**)を読み取り専用で使った。

| ☆ | maplenEnhancebot: `closePrice` 生値 | ÷1e18 後 | sf-history `end_price`(2026-11-18T15:00Z) |
|---|---|---|---|
| 0 | `14206476000000000000` | **14.206476** | **17.348802** |
| 10 | `107811940864000000000000` | **107,811.940864** | **209,944.513062** |
| 15 | `157629003016000000000000` | **157,629.003016** | **276,744.554911** |
| 21 | `157629003016000000000000` | **157,629.003016** | **154,306.054860** |

読み取り: **桁と小数の形が一致している**(☆0 が十数、☆10〜15 が十万台、小数6桁)。
∴ **sf-history の値は「1e18 で割った後の NESO」とすでに同じ単位**。そちらが `axes.sf[slot].prices` に使っている値と**そのまま比較・代入できる**。丸めは sf-history 側が `round(..., 2)` を**応答時にだけ**かけている(DB は6桁小数のまま)。新しい口では**丸めずに返す**つもり(必要ならそちらで丸めてください)。

**値そのものが一致しないのは単位ではなく時刻差**: sf-history は 2026-11-18T15:00Z で凍結、キャッシュは別時点。実測した日次ドリフトは 24h平均ベースで**中央値 9.2%/日・p90 28%/日**(§2-3)なので、7日離れて2倍近くなるのは正常な範囲。

**⚠ 高星域の注意**: 上の表の ☆15 と ☆21 は `closePrice` が**完全に同値**(`157629003016000000000000`)。上流は高い星で価格が頭打ちになる(このリポジトリには `scripts/audit_high_star_plateau.py` がこのクラスを監視するために存在する)。sf-history 側の ☆21 は 154,306 で別の値なので、**高星域で両者の一致を期待しないこと**。どちらが正しいかは別途の実測が必要で、今回の回答の範囲外。

### 2-3. 24時間平均の妥当性 → **妥当。点サンプルより良い。ただし `end_price` から計算すること。**

VPS の実データで測った(2026-11-04〜11-17、24時間すべて揃った (装備, 星, 日) = **8,096グループ** / 245,088行):

| 指標 | 中央値 | p90 | 最悪 |
|---|---|---|---|
| **日内の振れ幅** (max−min)/mean | **19.6%** | 34.1% | 89.8% |
| **JST 17:00(08Z) の1点** vs その日の24h平均 | **+2.4%** | +5.2% (p10: −2.9%) | 31.2% |
| 00Z(JST 9:00)の1点 vs 24h平均 | +6.9% | +17.0% | — |
| **24h平均そのもの**の前日比 | **9.2%** | 28.0% | — |

**判断の根拠**: 日内で約 **20%** 振れるのに対し、捉えたい変化(24h平均の日々の動き)は約 **9%**。
**点サンプルの誤差が、測りたい信号より大きい**。だから平均する方が正しい。平均の代償は「約9%/日のトレンドを半日ぶん遅らせる(≒4.6%)」で、取り除く 19.6% より小さい。

**JST 17時という時刻も、点で取るにしても偏りが小さい**(中央値 +2.4%)。リセット直後の JST 9:00 は +6.9%・p90 +17% で明確に高く出る。ユーザーの「9時台を避ける」判断はデータと一致している。

**ただし最悪ケースは 31.2%** なので、§2-1 の口は **24h平均を既定にしつつ最新点も併記**する。プランナー側は 24h平均を使い、画面では「今は平均より○%高い」を出せる形を推奨する。

**なぜ日内で振れるのかも実測で見えた**: 取引が無い間、価格は**1時間あたり一定額ずつ線形に減衰**する。
実測(item 1003720 ☆10、本日): `304497.522525 → 301358.372808 → 298219.223092`、差分が **−3,139.149717 で完全に一定**。
item 1152108 ☆21(11-18)も `159128.119074 → 156717.086967 → 154306.054860`、差分 **−2,411.032107 で一定**。
取引(`sum_enhance_count > 0`)が入ると跳ね上がり、そこから次の取引まで線形に落ちる。
∴ **24時間平均は「減衰のどこで測ったか」をちょうど打ち消す**量であり、この価格形成のしかたに対して理論的にも素直な選択。

## 4. この後の段取り(maplen-board 側)

本書は事実確認と回答のみ。実装は以下を計画書に落としてから(architecture-review を通し、ユーザー承認後に実装担当へ)。
論点として既に挙がっているもの:

1. PC 側の1日1回実行を、既存の `exp_ranking/bot/ops/LulumiDailyFetch`(経験値ランキング用、JST 09:05)に**相乗りさせるか別タスクにするか**。JST 17時という時刻指定があるので別トリガが素直。
2. VPS への増分の届け方。**新しい公開口は作らない**(依頼文の希望と一致)。gzip 235 KiB/日なので scp + 取り込みスクリプトで足りる。取り込み後に 4時間足を再導出(`rebuild_4h` 相当の差分版)。
3. 新しい軽い口の形と契約(`contract/response_fields.json` + 両側のテスト)。
4. 画面: 現在価格の非表示 / 「OpenAPI 復帰までは1日1回(JST 17時頃)更新」の明記 / 最終更新時刻の表示。**6ロケール同時追加**が規約。
5. **§1.1(2) の `ConnectionError` クラッシュ**。1日1回にする前に直す(リトライ or combo エラー扱い)。頻度を落とすと1回の失敗の重みが増える。
6. 復帰時に VPS timer へ戻せること(依頼文 (d))。既存の VPS 側の仕組みは消さない。
7. 対象装備は **34グループのまま**(依頼文のとおり、広げない)。

**対象外として確認したこと**: `data/sf_history_items.json` の 34 グループ以外の装備(指輪3・ペンダント1・エンブレム・サブ武器)は sf-history に1行も存在しない(hourly は 34装備ぶんのみ)。そちら側で「登録時点の価格」を使い続ける前提は、こちらのデータと矛盾しない。
