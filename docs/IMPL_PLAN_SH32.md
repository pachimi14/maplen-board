## 1. ★判定範囲と表示範囲は違う(ユーザー裁定 2026-08-15)

> ☆23〜25 は DISCOVERY の条件には不要。ただし、DISCOVERY と判定された装備については
> SF の強化費一覧として**すべて**出したい(22までしか表示しないのはこちらの都合でしかない)。

| | 範囲 | 根拠 |
|---|---|---|
| **判定**(監視対象に入れるか) | **`itemUpgrade` 0〜21**(=☆1〜22 の帯) | 下記 |
| **表示**(価格一覧に出す帯) | **`itemUpgrade` 0〜24**(=☆1〜25 の帯) | ユーザー指示 |

**判定から ☆23〜25 を外す理由(実測)**: この帯は「まだ誰も到達していない」だけで、
新装備かどうかと無関係。**150日の履歴を持つ既存の Arcane Umbra Staff ですら ☆24・☆25 は DISCOVERY**。

```
判定範囲を 0..21 にすると   : 15装備(= 代表3件)
判定範囲を 0..24 にすると   : 217装備(うち202は ☆23-25 だけ)
  帯ごとの内訳: ☆23=177装備 / ☆24=217装備 / ☆25=217装備
```

**★217装備を5分ポーリングすると 62,496リクエスト/日**(既存ジョブ全体 3,696/日)。
判定を 0..21 に絞ることで **864リクエスト/日**に収まり、記録が現実的になる。

## 2. スコープ(3つの独立した部品)

### A. 日次スキャン(検出)

**新規スクリプト + timer。1日1回。**

1. `/stats/enhance-group` → `/stats/enhance-group/items` で **472装備を列挙**
2. 各装備の Open API を引き、**`itemUpgrade` 0〜24 の `step` を全部記録**
3. **`itemUpgrade` 0〜21 に DISCOVERY を1つでも持つ装備**を「監視対象」にする(§1)

- **遅延は既存 `fetcher.Fetcher` の作法に従う**。429 は既存のバックオフに委ねる
- **部分成功でよい**(1装備の失敗で全体を落とさない)。**失敗数を必ずログに出す**
- **走査の記録は生のまま残す**(15装備ぶん)。**畳み込みは下の A-1 で行う**

#### A-1 ★代表への畳み込み(ユーザー裁定 2026-08-15)

> 15装備ではあるが、実際はグループ3つ。既存ページと同様に**代表グループの3つのみポーリング**し、
> **同名で検索できるように**。数値は代表に合わせて同じものを表示する。

**既存 `sf_history_items.json` の代表 / `aliases` の仕組みと同じ形にする**(新しい概念を作らない):

- **グループの単位は `/stats/enhance-group/items` の `(equipLevelType, equipType, equipPartType)`**
  — 装備名から推測しない。**列挙 API が返すグループをそのまま使う**
- **代表の選び方は既存 `pick_representative_item()` と同じ規則**(週間強化回数が最大のもの)。
  **別の規則を発明しない**
- **`aliases` に15装備すべての `itemId` と `itemName` を持つ**
- F7(価格完全一致)は**実測済みだが、畳み込みの前提として毎回検証すること**:
  スキャン時に**代表と alias の `step` が全帯で一致しない場合は畳まず、警告をログに出す**
  (**黙って代表の数字を全員に配らない**。将来ゲーム側の仕様が変わったときの検出器)

### B. 監視ポーリング(記録)★唯一の取得経路

**監視対象の代表だけを5分ごとに取得し、新規テーブルへ追記。**

- **叩くのは代表 itemId のみ**(現在3件)。**alias は叩かない**(A-1)
- **`itemUpgrade` 0〜24 の全25帯**を記録する(表示範囲に合わせる)
- 記録するのは **(itemId, itemUpgrade, 価格の時刻窓, price, step)**
- **`currentPrice` と `previousPrice` の両方を保存**(1回で2点得られる)
- **同じ `(itemId, itemUpgrade, startDate)` は1行**(upsert)。重複で行が増えないこと
- **監視対象がゼロなら何もしない**(将来 DISCOVERY が全て終わったら自動的に静かになる)
- 負荷: **代表3件 × 288回/日 = 864リクエスト/日**

**★狙いは `DISCOVERY → CHANGE` に切り替わった瞬間の記録。**F2/F3 により、記録しなければ**永久に失われる**。

**★5分間隔で受け入れる精度の劣化(承知のうえの選択)**: F9 のとおり上流は毎分更新するが、
`previousPrice` で拾えるのは1分前まで。∴ **5分のうち3分ぶんは観測されない**。
**遷移の時刻は「5分の幅」までしか特定できない。**
**この幅を隠して「何時何分に終わった」と書かないこと。**

### C. 専用ページ(表示)

**新ルート `#/starforce/discovery`。★上流を叩かない**(ユーザー裁定):

> 5分ポーリングしてそれをそのまま使用すれば、リクエスト時に API を叩く必要もない。

- **B が書いた DB を読むだけ**。**リクエスト時の上流アクセスはゼロ**
  (∴ アクセスが増えても上流負荷は一定。既存 `LatestPriceCache` はこのページでは使わない)
- **★観測時刻を必ず表示する**(「〜時点」)。DB を読むだけなので、
  **ポーラーが止まると黙って古い値を出し続ける**。それを利用者が見抜けるようにする
- 一覧: **監視対象の装備**。**F7 のとおり職業違いは代表に畳む**(**5行に増やさない**)
- 各装備を開くと **☆1〜25 の全25帯の強化費一覧**(§1)
- **DISCOVERY の帯にバッジを付ける**(ユーザー指示。**このページ限定**)
- **「最近終了」**: 最後の DISCOVERY 帯が CHANGE になった装備を **30日間**出す
  - **★記録は永久に残す**(表示期間だけの話)。**表示日数は設定で変えられること**
  - 遷移時刻は**幅を持った表現**で出す(上記)
- **既存の `#/starforce` は1ピクセルも変えない**
