# IMPL_PLAN_SH18 — 足のラベルを区間終了時刻にする

前提: SH-17 完了・統括検収済。**ユーザー裁定 2026-08-05**。

## 0. 背景

ユーザー指摘:
> `8/5 0:00` の表記で実際は `4:00` 時点の数値というのは非常にわかりにくい。

**指摘は正しい。** 4時間足の値は **区間内の最後の `end_price`**(= 区間終了時点の価格)である
(設計 §9「代表値 = 区間内で最後に存在する時刻の `endPrice`」)。
∴ `00:00–04:00` の足の中身は**実質「04:00 時点の価格」**であり、
**開始時刻でラベルするのは実態とずれている**。

**ユーザー裁定**: **足のラベルを区間終了時刻にする**(設計 §8「ラベルは区間開始」を反転)。

## 1. ★これは決定の反転である

- 設計 §8 / §9 の「**ラベルは区間開始**」を**反転**する
- SH-3(`labelIs: "bucketStart"`)/ SH-11 / SH-14 の表示はこの規約に乗っていた
- **旧文は書き換えず、反転として追記する**(設計書 §8 に追記)

## 2. ★サーバー・DB は触らない

**保存とAPIは開始時刻のまま。表示時に +4時間する。**

理由:
- `sf_price_history_4h` の `price_at` の意味を変えると、**再生成の決定性・過去の検収値との対応が壊れる**
- API の `date` / `endDate` / `provisionalDate` の意味を変えると、SH-13〜SH-17 の全検収が読み替えになる
- **表示の問題は表示層で解く**

∴ `labelIs` フィールドの値は**サーバーの意味を表すのでそのまま**(`bucketStart`)。
**クライアントが表示時に変換する**ことを README とコメントに明記する。

## 3. 変更後の表示

| 点の種別 | 表示する時刻 | 範囲の注記(SH-17) |
|---|---|---|
| **確定した足** `[T, T+4h)` | **`T+4h`** | `T–T+4h の足` |
| **暫定の足**(完成済み未保存) | **`T+4h`** | `T–T+4h の足` |
| **未終了の足**(進行中) | **現在時刻(`asOf`)** ← SH-17 のまま | `T–T+4h の足(未終了)` |

**未終了の足は終了時刻がまだ来ていないので、終了時刻でラベルしない**(未来の時刻を表示しない)。
SH-17 の「現在時刻を出す」を**維持**する。

## 4. ★ヒートマップも同じ規約に揃える

**セルの割り当てを「区間終了時刻」の曜日・時刻で行う。**

- 例: `水 20:00–木 00:00` の足 → **`木` 行の `00:00` 列**
- 列見出しは **`00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00`**(終了時刻。集合は同じ)
- 行の順は **木 → 金 → 土 → 日 → 月 → 火 → 水**(SH-14 のまま)
- ∴ **左上 = 「木曜 00:00 時点の価格」**(ユーザーの「木曜 UTC 00:00 を開始地点」の要求を満たす)

**★結果として各セルの中身が1枠ずれる。これは意図した変更である。**
ラベルだけ変えて中身を据え置くと、**今回指摘された不整合をヒートマップ側に作り直す**ことになる。

## 6. 受け入れ基準

- **(a)** チャートの確定・暫定の足の時刻が **`T+4h`** になる。
  実例: API の `2026-08-05T00:00:00Z` の点が **`04:00`** と表示される
- **(b)** **未終了の足は現在時刻のまま**(未来の時刻を表示しない)
- **(c)** 範囲の注記(SH-17)は**開始–終了のまま**(`00:00–04:00 の足`)。ラベルと矛盾しない
- **(d) ★ヒートマップの1枠ずれを機械確認**:
  **新しい `[木][00:00]` の中央値と件数が、旧実装の `[水][20:00]` と一致する**ことを示す
  (旧の値は `docs/reports/SH11_LOCAL_TIME_HEATMAP.md` / `SH14_UTC_AND_ORDER.md` にある。
  必要なら旧アルゴリズムを一時的に再現して突き合わせてよい)
- **(e)** 左上セルが **「木曜 00:00」**
- **(f) ★統計不変**: `computeStats`(平均・高値・安値)と `currentPercentile` が
  **ラベル変更前と1ビットも変わらない**(これらは時刻に依存しないため)
- **(g)** `n` の合計が確定点数と一致(取りこぼしゼロ)。暫定点は入らない
- **(h)** `npm run test` 全緑 / `npm run build` 成功 / **`server/` の差分ゼロ**
- **(i)** 6ロケールのキー数一致
- **(j)** SH-7〜SH-17 の性質維持

## 7. 停止条件

1. **(f) が崩れる**(統計がラベル変更で動く)→ どこかで時刻に依存している。**止めて報告**
2. **(d) の一致が取れない**(1枠ずれの検証が合わない)→ 割り当ての解釈がずれている
3. `server/` を変えないと実現できない
4. §5 の「触らないもの」に触る必要が生じた / 新規依存が必要になった
