## 0. 事前に判明したこと(スクリプト作成前の最小限の探索)

`history` エンドポイントは maplenEnhancebot 側に前例が一切なく(`latest` しか使われていない)、
パラメータの単位・省略時挙動が**どこにも文書化されていなかった**。`probe.py` を正しく組むために、
本番スクリプトの前に最小限の探索呼び出しを行った(内訳は §8 に記載、`probe.py` 完成後の
公式走行とは別枠)。ここで判明した、設計書からは読み取れなかった事実:

- **`minTimestamp` / `maxTimestamp` は Unix epoch 秒**(ミリ秒ではない)。ミリ秒を渡すと
  **エラーにならず** `"points": []` を返す(範囲外の未来日付として解釈されるため無言で空になる、
  という**サイレント障害モード**)。これを知らずに実装すると「history にデータが無い」と誤診断する
- `period=0` / `period=6` / `period=7` は HTTP 400(`failed command validation`)。`period=1..5` は 200
- `itemUpgrade` を省略すると **`itemUpgrade=0` を明示指定したときと同一の応答**が返る(全星ではない)
- `itemUpgrade=25` は HTTP 500(400 でも空応答でもない)

これらは `probe.py` に組み込み済みで、以下の測定はこの正しいパラメータで実行している。

## M1 — `history.endPrice` と `latest.closePrice` のスケール関係(P2・最優先)

**結論: `closePrice`(raw)= `endPrice` × 1e18。design の前提 P2 は真。**

`latest` のスナップショット時刻 `latestUpdatedAt = 2026-08-04T16:40:00Z` に対し、`history` の
**直近1時間足**(`date = 2026-08-04T16:00:00Z`)の `endPrice` と比較:

| itemUpgrade | endPrice(history 直近足) | closePrice(raw, latest) | 比 closePrice/endPrice |
|---|---|---|---|
| 0  | 413352.802423   | 413352802423000000000000   | 1.0000000000000000e18 |
| 10 | 2293229.756863  | 2293229756863000000000000  | 1.0000000000000001e18 |
| 17 | 3951165.611808  | 3951165611808000000000000  | 1.0000000000000000e18 |
| 21 | 2711584.243397  | 2711584243397000000000000  | 1.0000000000000001e18 |

- **平均比 = 1.000000000000000e18、4点間の最大相対ばらつき = 1.28e-16**
  (受け入れ基準(b)の閾値 1e-6 を6桁以上下回る。この程度のばらつきは float64 で
  10^18 を厳密表現できないことによる浮動小数丸めそのもので、実質ビット一致とみなせる)
- **1つ手前の足**(`15:00:00Z`)の `endPrice` で同じ比を取ると 0.98〜1.25e18 とばらつく
  (例: itemUpgrade=17 で 1.247e18)。これは単位不一致ではなく、`latest` のスナップショット時刻と
  1時間ずれた足を比べたことによる**実際の価格変動**。→ **時刻を厳密に合わせれば比は 1e18 に
  高精度で一致する**ことも同時に確認できた(単位换算係数の一意性の追加証拠)

## M2 — `itemUpgrade` を省略すると全星が返るか(P4)

**結論: 返らない。省略時は `itemUpgrade=0` を明示指定したのと同一の応答になる。**

- `itemUpgrade` を省略して10日分を要求 → 応答本体に `"itemUpgrade": 0` が明示され、
  `points` は235件(`itemUpgrade=0` を明示した場合と同一件数)
- ∴ **P4 は偽**。1装備の全星(22段階)を取るには itemUpgrade ごとに個別リクエストが必要
  (design §5.3 の見積り「616 リクエスト」側が確定。「28 に減る」楽観シナリオは成立しない)。
  この結果は **SH-2/SH-3 のリクエスト量見積りに影響する**(§9 統括への申し送り参照)

## M3 — 1時間足で遡れる最古の時刻(P1)

**結論: 最古 `2026-03-08T01:00:00Z`。現在(`2026-08-04T17:14 UTC` 時点)から 149.7 日前。**

- 200日分(`minTimestamp` を現在から200日前)を要求したが、返ってきたデータの最古日付は
  149.7日前で止まっていた(要求ウィンドウ全体は満たしていない)。つまり **これは応答件数の
  頭打ちではなく、実際の保持期間の限界**(§M6 で追加検証)
- design の前提 P1「直近150日」は**ほぼ厳密に一致**(149.7日)。**P1 は真**

## M4 — 有効な `itemUpgrade` の範囲

**結論: `latest` は 0..22(23段階)。`history` は 0..24 まで 200 を返すが、実データがあるのは 0..22
(この装備の最大強化段階と一致)。25 は 500。**

- `latest` の `starForce` 配列: `itemUpgrade` は **0, 1, 2, …, 22**(23件、全て `closePrice` あり)
- `history` エンドポイントを itemUpgrade=22/23/24/25 で個別に照会(10日分):

  | itemUpgrade | status | 返った件数 |
  |---|---|---|
  | 22 | 200 | 235(通常どおりデータあり) |
  | 23 | 200 | 0(パラメータは受理されるが空) |
  | 24 | 200 | 0(同上) |
  | 25 | **500** | — |

- ∴ パラメータの受理範囲(エラーにならない範囲)は少なくとも 0..24、**この装備の実データが
  存在する範囲は 0..22**(`latest` と一致)。25 はサーバーエラーになる(400 でも空でもない)

## M5 — `sumEnhanceCnt=0` の時間帯にも `endPrice` があるか(P3)

**結論: ある。3510行中3111行が `sumEnhanceCnt=0` で、そのうち3111行(100%)に non-null `endPrice`。**

- 全行数: **3510**
- `sumEnhanceCnt=0` の行数: **3111**(88.6%)
- そのうち `endPrice` が non-null の行数: **3111**(=100%。`sumEnhanceCnt=0` だからといって
  `endPrice` が欠けることはない)
- **P3 は真**。`endPrice` は実際の強化イベント有無に関わらず連続的に存在する計算値

## M6 — 1リクエストの所要時間と返る点数、点数の上限

**結論: 中央値 140ms(n=5)。1レスポンスで3510点(150日分の全量)が1回で返る。ページングやカーソルは
観測されず、応答件数の頭打ち(§M3)は保持期間の限界であって1レスポンスあたりの件数キャップではないと
推測されるが、両者が同じオーダー(150日≈3600点)のため完全な切り分けはできていない(下記に明記)。**

- 所要時間(itemUpgrade=0, 200日分要求, n=5): `156, 125, 141, 140, 125` ms → **中央値 140ms**
- 1レスポンスの点数: **3510点**(200日分=最大4800時間を要求したが、実際の保持期間 149.7日分
  ≈ 3592時間ぶんが1回の応答で返った。`hasMore` やカーソル等ページング情報はレスポンスに存在しない)
- 期待点数(連続なら): 3592(=最古〜最新の時間差から算出)。実際 3510 → **差82点(2.3%)は
  欠損**(飛んでいる時間帯がある。障害/遅延によるものと推測されるが原因は未調査)
- **未解明点(watch-item)**: 「150日を超える要求で応答が3600点前後より多く返ることがあるか」は
  未検証(要求200日に対し実データが149.7日しかなく、レスポンス件数の天井を独立に確認できなかった)。
  実運用上は問題にならない(design が必要とするのは150日分であり、それは1リクエストで返ることを
  確認済み)が、「本当に上限が存在するかどうか」は未決のまま。次スライスで150日を明確に超えるデータが
  蓄積された時点(またはより古いデータを持つ別itemIdで)に再確認する余地がある

## M7 — `period` パラメータの意味

**結論: `period=2` は1時間足。連続する `date` の差は最小・最頻値ともに3600秒(1時間)。**

- 200日分レスポンス内の連続する `date` の差(秒)の集合: **{3600, 7200, 10800, 14400}**
- 最小値かつ最頻値は **3600秒 = 1時間**。7200/10800/14400 は §M6 で述べた欠損(1〜3時間分の
  行が飛んでいる)によるギャップであり、粒度そのものは常に1時間
- `period=0,6,7` は HTTP 400、`period=1,3,4,5` は 200 で受理されるが、**それらの意味は本スライスの
  範囲外(M7 は period=2 についてのみ問われている)のため未検証**。今後 4時間足設計(design §9)で
  `period` を直接使う予定がある場合は別途確認が必要

## 停止条件チェック

1. M1の比が不一定 → **該当なし**(4点とも1e18に高精度一致)
2. 429受信 → **該当なし**(0件)
3. 401/403等のアクセス拒否 → **該当なし**(全て200、一部400/500だが認証起因ではない)
4. パラメータ名・レスポンス構造が §2 の記述と違う → **部分的に該当**。§2 は `minTimestamp` /
   `maxTimestamp` の単位を明記していなかった(実測: **秒**)。これは「間違っていた」というより
   「未記載だった」に近いが、正しい形を §0 に実測で記録した。エンドポイント自体・主要パラメータ名
   (`itemId`, `itemUpgrade`, `period`, `minTimestamp`, `maxTimestamp`)は計画書の記述どおり有効だった
5. 設計書との矛盾 → **軽微な1件のみ、§9 参照**(停止を要する矛盾ではないと判断し実測を継続。
   理由: 設計書 P1〜P3 は真であることが確定し、当初の危惧「P2を外すと全数値が1e18倍ずれる」は
   回避された。P4=偽は設計書自身が「要検証」と明記していた分岐の一方が確定しただけで、
   設計の前提の崩壊ではない)
6. 「触らないもの」に触れる必要が生じた → **該当なし**
7. 60リクエストに達しても測定項目が埋まらない → **該当なし**(45リクエストで全項目確定)

**停止条件はいずれにも該当しないため、調査を完了として報告する。**

## 8. 総リクエスト数の内訳(正直な申告)

`probe.py` の**1回の走行**は 14 リクエスト(`latest` 1 + `history` 13、429=0)。
これは `docs/reports/sh1_samples/request_log.json` に完全なログがある。

**それに加えて**、`probe.py` を書く前に、`minTimestamp`/`maxTimestamp` の単位(秒かミリ秒か)や
`period` の有効値、`itemUpgrade` 省略時の挙動を確かめるための**最小限の手動探索**を行った
(17リクエスト、`latest` 2 + `history` 15、うち400が4件・429は0件)。これは公式に前例のない
エンドポイントを安全に叩くための正常な手順だが、実際に公式APIへ負荷をかけているため
正直に計上する。

さらに、`probe.py` の完成後の確認中に**誤って2回目の走行**(別出力先 `/c/tmp_probe_verify`、
リポジトリ外・成果物には含まれない)を行ってしまった(14リクエスト、追加の429なし)。
これは避けられたはずのミスであり、本来不要だった。当該出力ディレクトリは削除済み。

| 区分 | latest | history | 400 | 500 | 429 | 小計 |
|---|---|---|---|---|---|---|
| 手動探索(パラメータ発見) | 2 | 15 | 4 | 0 | 0 | 17 |
| `probe.py` 公式走行(成果物の元) | 1 | 13 | 0 | 1 | 0 | 14 |
| `probe.py` 誤った再走行(手違い・成果物に不使用) | 1 | 13 | 0 | 1 | 0 | 14 |
| **合計** | **4** | **41** | **4** | **2** | **0** | **45** |

**合計45リクエスト ≤ 60、429は0件で受け入れ基準(c)を満たす。** ただし2回目の走行は
本来不要だった手違いであり、**次に同種の調査を行う際は「確認のための再走行」を安易に
行わない**ことを自戒として記録する。

## 9. 統括への申し送り(気づいたが本スライスでは扱わなかったこと)

- **P4=偽の影響**: design §5.3 は差分取得のリクエスト数を「28〜616」と幅を持たせていたが、
  本測定で **28には縮まらないことが確定**(itemUpgrade省略は全星を返さない)。差分取得は
  常に28装備×22段階=616リクエスト相当になる(4時間ごとの差分取得ウィンドウ=直近8時間なら
  1リクエストあたりのペイロードは小さいので負荷自体は小さいが、**リクエスト数の見積りは
  616側で計画すべき**)。§5.3 の記述更新を推奨
- **P10(VPS空き容量・RAM・Caddyfile実物・空きポート)は本スライスで測定していない**。
  design §13 の SH-1 行はP10もSH-1のスコープとして記載しているが、**承認済み `IMPL_PLAN_SH1.md`
  の §1〜§3 にはVPS関連の調査項目・成果物が一切含まれておらず**(測定項目はM1〜M7のみ、
  作るものは4つの新規ファイルのみ)、VPSへのアクセス手段も計画書に記載がない。
  計画書の記述に従い、VPS調査は行わなかった。**design と実装計画の間にスコープの食い違いが
  ある**(design は P10 を SH-1 に含める想定、承認済み計画は含めていない)。次のいずれかで
  解消することを推奨:
  - 選択肢A: P10 調査を独立の小スライス(例 SH-1b)として別途起票する
  - 選択肢B: design §13 の SH-1 行から P10 を外し、SH-3(サービス構築)や SH-6(本番投入)の
    受け入れ基準に統合する
  - **推奨: A**(SH-1のスコープを汚さず、かつ VPS 実測の抜け漏れを可視化できる。
    IMPL_PLAN_SH1 は M1〜M7 だけで十分に完結しており、無理にP10を混ぜる必要はなかった)
- **応答に `sumEnhanceCnt=0` の行が88.6%** という高い比率は、design §6.1 の
  「統計は確定足のみで計算する」方針にとって好材料(取引が薄い時間帯でも `endPrice` が
  連続的に埋まるため、チャートの欠損が想定より少なくて済む可能性が高い)
- **`itemUpgrade=25` が 500 を返す**ことは、SH-3 で `history` を叩くコードを書く際に
  「起こりうる有効範囲の1つ上」を渡さないようにする実装上の注意点として申し送る
  (`requiredPriceStars` の返す集合が 0..21 の範囲に収まっていれば実運用では踏まない見込みだが、
  念のため)
