## 0. A の背景

現状の表示: **「現在の位置 / この期間の13パーセンタイル」**。

実装の定義(`series.js:199`)は
`percentile = (期間内で「今の値以下」だった点の割合) × 100`。
∴ **13パーセンタイル = 期間内の 87% の時点より今のほうが安い**。

**数値としては正しいが、読み手が方向を自分で反転しないと意味が取れない。**

**ユーザー裁定**: **「この期間の 87% より安い」**という表現にする。

## 2. A — パーセンタイル表現

### 2-1 表示

```
現在の位置
この期間の 87% より安い
```

- 表示する数値は **`round(100 − percentile)`**
- **端の扱いを決めてテストで固定する**:
  - `percentile = 0`(期間内のどの時点より安い)→ **「この期間で最も安い」**
  - `percentile = 100`(どの時点より高い)→ **「この期間で最も高い」**
  - 丸めで 0% / 100% になる場合も、上の2文言に落ちないよう**実際の順位で判定**する
    (「0% より安い」のような無意味な文が出ないこと)
- **6ロケール同時**に文言追加。**断定的な推薦をしない**(「今が買い」等は書かない)

### 2-2 ★計算式は変えない

`currentPercentile` の定義(`≤ current` の割合)は**そのまま**。
**表示側で `100 − x` にするだけ**。
理由: 統計の意味を変えると SH-11 以降の検収値との突き合わせができなくなる。

## 3. B — 20分スタンプの表示

- **「現在値」サマリーカードに、その値の時刻として添える**
- **UTC 表記 + 曜日**(SH-14 の規約に合わせる)
- **計算条件ブロックは復活させない**。現在値カードの補助表示に留める
- 現在価格が取得できないときは**時刻も出さない**(履歴で代替しない)

## 4. C — キャッシュを上流の周期に合わせる

### 4-1 観測(統括)

`latestUpdatedAt` を時間を空けて4回観測 → `04:00 / 04:20 / 04:40 / 05:00`。
**すべて20分グリッド上**。現行の固定 300秒 TTL は**上流より細かく叩いているだけ**。

> **4サンプルの観測であり恒久保証ではない。**§4-3 のガードはそのための保険。

### 4-2 変更後

```
next_publish = latestUpdatedAt + 20分
expiry       = next_publish + grace(既定 60秒)
```

### 4-3 ★必ず守るガード

- **上限**: `expiry − now` は **20分(1200秒)を超えない**(ユーザー指定の「最大20分」)
- **下限**: `expiry − now` は **60秒を下回らない**。
  **`latestUpdatedAt` が古いと失効が過去になり、毎リクエスト上流を叩く事故**になる。
  **これが本スライスで最も危険な失敗モード**
- **スタンプが取れない/不正/未来 → 固定20分にフォールバック**(推測で細かく叩かない)
- **single-flight は維持**
- 環境変数: `SF_HISTORY_LATEST_PUBLISH_INTERVAL_SECONDS`(既定 1200)/
  `SF_HISTORY_LATEST_GRACE_SECONDS`(既定 60)。
  既存の `SF_HISTORY_LATEST_TTL_SECONDS` は**「上限」の意味に読み替えるか廃止**し、**README に明記**する

> **注**: 中断されたエージェントが `fetch_latest.py` に残した未コミットの実装(86行・テストゼロ)は
> **統括が破棄済み**。**HEAD の状態から作り直すこと。**

## 5. 受け入れ基準

- **(a)** 表示が「この期間の N% より安い」になる。**端(最安・最高)の文言がテストで固定**されている
- **(b)** `currentPercentile` の**計算式が無改変**(`git diff` で示す)。
  統括の検収値(SH-11 系)と**同じ数値**が出ること
- **(c) 失効の計算**を単体テストで固定(時計を注入・**実 API を叩かない**):
  通常 / **スタンプが1時間前 → 下限60秒** / **不正・欠落 → 20分** / **どの場合も20分を超えない**
- **(d)** 20分の窓で同一 itemId の上流アクセスが **2回を超えない**
- **(e) single-flight 維持**(既存テストが無改変で緑)
- **(f)** 現在値カードに **UTC 時刻 + 曜日**でスタンプが出る。取得失敗時は時刻も出ない
- **(g) 計算条件ブロックが復活していない** / **UTC 統一が崩れていない**
- **(h) `/prices` 無影響**: 暫定点・`endDate`・`provisionalDate`・**4h テーブルのハッシュが不変**
- **(i)** `pytest` 全緑(オフライン)/ `npm run test` 全緑 / `npm run build` 成功
- **(j)** 6ロケールのキー数一致
- **(k)** SH-7〜SH-14 の性質維持

## 6. 停止条件

1. **下限ガードと「最大20分」が両立しない**と判明した
2. 実データで **`latestUpdatedAt` が20分グリッドでない**証拠が出た
   → **止めて観測値を添えて報告**(統括の観測は4サンプル)
3. 表示だけでは A を実現できず `currentPercentile` の計算式変更が要る
4. §1 の「触らないもの」に触る必要が生じた / 新規依存が必要になった
