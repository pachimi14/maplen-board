## 1. ★方針(ユーザー裁定)

> ユーザーは**現時点での強化費**を見ており、形成後は形成後の価格として見ることになる。
> いま強化するなら、**未形成の価格で費用を考えるのが普通**。

∴ **表示する数字は「いま強化した場合の費用」であり、過小でも概算でもない。**

- **「実際より少なめ」「概算値」といった評価を書かない**
- **「安い」「お得」も書かない**
- **書くのは「どの帯が価格形成中か」という事実だけ**

## 2. A — 3種を装備リストに追加

### 2-1 ★カタログに載っていない(既存の追加手段が使えない)

既存の `ADDITIONAL_ITEM_IDS`(Magic Eyepatch / Berserked / Dreamy Belt)は
**maplenEnhancebot の `catalog/main_equipment.json` に存在する**装備だった。
**この3種はそこに載っていない**(統括が確認済み)。∴ 名前と alias が解決できない。

**解決策**: **dynamicpricing の列挙 API を使う**。
`POST /stats/enhance-group` → `GET /stats/enhance-group/items` で
**472装備とグループ(= alias 集合)が取れる**。`scripts/scan_discovery.py` が既に使っている経路。

- **maplenEnhancebot に書き込まない**(読み取りのみ)
- **既存30装備の解決経路を変えない**(カタログ由来のものはカタログのまま)。
  **新経路は「カタログに無い装備」だけに使う**
- **代表は SH-32 と同じ規則**(`discovery.pick_representative_item`、同点は itemId 昇順)。
  **既存の discovery 側で固定済みの代表があるなら、それに合わせる**
  (同じ装備が2つの表で別代表になると混乱する)

### 2-2 バックフィル

## 3. B — 未形成帯の計算

**履歴のある帯は実履歴、履歴の無い帯は現在価格を全期間の定数として使う。**

- **現在価格の取得元は上流の実値**。**`0.000001` 等の定数をハードコードしない**(H2)
- **「形成中かどうか」は上流の `step` で判定する**(SH-32 F1)。
  **価格のしきい値で判定しない**
- **判定は3種に限定しない**。将来どの装備でも同じ経路で動くこと
- **全帯に履歴がある装備の計算は1ビットも変えない**(既存31装備の回帰ゼロ)

### 3-1 ★過去の足について正直であること

未形成帯は**過去も「いまの値」で埋まる**。実際には過去はもっと安かった(価格は育つ)。
**この差は Hat で合計約 7,300 NESO / Expected 15億に対し 0.001% 未満**なので実害は無いが、
**「過去の実測値を描いている」と誤解させる表現をしない**こと。

## 4. C — 注記

チャートに **どの帯が価格形成中かを表示する**。

```
☆1〜10 / ☆20〜22 は価格形成中
```

- **帯の範囲を必ず明示する**(「一部の帯が」で済ませない)。
  **範囲さえ出れば、高星ほど効くことは読者が判断できる**
- **評価・警告・推奨を書かない**(§1)
- **形成中の帯が無い装備では注記を出さない**
- **6ロケール同時**。用語は New Equipment と揃える(**価格形成中**)
