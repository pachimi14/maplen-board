## 2. A — 記録

### 2-1 新しいテーブルにする(既存テーブルを変更しない)

`sf_discovery_price_history` の主キーは `(item_id, item_upgrade, price_at)` で、
**キューブは `item_upgrade` で識別できない**(キューブ種の itemId で識別する)。

∴ **新テーブル `sf_discovery_cube_price_history`** を作る。主キーは
**`(item_id, cube_item_id, price_at)`**。列は既存テーブルと同じ流儀
(`end_at` / `price` / `step` / `fetched_at`)。

- **既存テーブルにカラムを足さない**(**稼働中で 4,350行以上の実データが入っている**。マイグレーション不要にする)
- **`currentPrice` と `previousPrice` の両方を保存**(既存と同じ)
- **upsert**。同じ `(item_id, cube_item_id, price_at)` で行が増えないこと
- **価格の変換は既存と同じ `PRICE_DIVISOR`**

### 2-2 ★キューブ名をハードコードしない

上表の6種は**今日の観測**であり、**将来増減しうる**。

- **キューブのコードは応答から来たものをそのまま保存**する
- **表示名は Navigator metadata(`/metadata/items/{id}/info` の `metadata.common.itemName`)から解決**し、DBに保存する
  (**日次スキャンで、未知のコードだけ解決すればよい**。毎回6件引き直さない)
- **名前が解決できないコードは、コードのまま表示する**(**画面が壊れない**こと。**推測した名前を出さない**)
- **6種を定数として列挙しない**。**応答に7種目が現れたら自動で載る**こと

### 2-3 監視条件は変えない(G5)

**判定は現行どおり SF の `itemUpgrade` 0〜21 のみ。**
キューブの状態を判定に使わない。**キューブは記録と表示だけ。**

理由: 実測で**キューブだけ形成中の装備は0件**であり、条件に足しても**1件も増えない**。
足せば「☆23〜25 を条件に入れると217装備になる」のと同種のリスクだけが増える。

## 3. B — API

- `/sf-history/discovery/prices` の応答に **キューブの配列を追加**する
  (SF の `bands` と**並列の別フィールド**。`bands` の中に混ぜない)
- 各要素: **キューブのコード / 表示名 / 価格 / `step` / 遷移時刻(`windowStart`/`windowEnd`、未観測は `null`)**
- **遷移時刻の導出は SF と同じ仕組み**(`discovery.find_transition` を再利用。**別ロジックを作らない**)
- **並び順は決定的**にする。**階層・強さの序列を発明しない**
  (コード順で構わない。**「上位キューブ」等の順位付けをしない** — 根拠が無いため)
- **`contract/response_fields.json` を更新**し、契約テストを緑に保つ
- **既存4エンドポイントの既存フィールドを1つも削除・改名しない**

## 4. C — 表示

**SF 表の下に、同じ形のキューブ表**を置く。

| 列 | 内容 |
|---|---|
| キューブ | 表示名(解決できなければコード) |
| **価格 (NESO)** | **SF 表と同じ書式**(小数6桁固定・右揃え・`tabular-nums`) |
| 状態 | **価格形成中 / 形成済み**(SF と同じ語) |
| 形成済みになった時刻 | **SF と同じ規則**(未観測は `-`・幅のある表現) |

- **SF 表と同じ見た目・同じ語**にする(**別の用語・別の書式を作らない**)
- 表の見出しで **SF とキューブの区別**が付くこと
- **キューブが1件も無い装備では、表ごと出さない**(空表を出さない)
- **ゲーム内の仕様を説明しない**(読者は知っている)
