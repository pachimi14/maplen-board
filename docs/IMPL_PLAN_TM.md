## 0. 目的と背景

- **要件を一文で**: MapleStory N を起動したら「今日やること・リセットまでの時間・イベント期限が一目で分かり、とりあえず開いておくページ」を作る。
- **北極星への寄与**: 「毎朝の習慣」の器を EXP ランキング以外にも広げ、**滞在の中心(将来 Dashboard の中核)**にする。※このページ自体は検索/SNS流入を狙わない(OG不要・後述)。流入寄与は間接的で、主目的は**習慣化とサイト内滞在の深化**。
- **参照する決定**: LULU-040(静的配信が正)/ LULU-041(同一オリジン・localStorage共有)/ LULU-005(historyKey)/ LULU-007(i18n 6ロケール)/ LULU-008(localStorage命名)。TM は roadmap の T0〜T12 に無い**新規イニシアチブ**——着手前に DECISION_LOG へ新エントリ(スコープ・北極星寄与・統合方式)を起こす。

## 1. スコープ

### MVP に含む(仕様書 §MVPのゴール が正)
- **タスク種別4種**: Daily / Weekly / Monthly(優先度低)/ Event
- Daily/Weekly: リセット残時間表示・運営プリセット・ユーザー独自タスク・完了チェック・通知対象フラグ
- Event: 期間(開催/報酬受取/ショップ交換)を持ち、内部に Daily/Weekly/期間中1回 のタスクを内包・期限表示
- **運営プリセット**の読み込みと、ユーザー側カスタマイズ(有効化/非表示/並び替え/通知対象/キャラ割当)
- **ブラウザ保存**(localStorage・ログイン不要・永続)+ **バックアップ/復元**(JSON エクスポート/インポート)
- リセットによる自動更新(残時間カウントダウン・日跨ぎ処理)

### MVP に含まない(将来・明示的に後回し=「作らないリスト」判定済み)
- **Discord通知**(OAuth/DM/スケジューラ = **バックエンド必須。VPS `api.lulumi-tools.com` に将来実装**、LULU-042 系。Pages では不可)
- **Dashboard 統合UI**(TM は単独完結。Dashboard は TM の進捗を後で消費)
- **EXP/Navigator 連携**(現在EXP・今日の獲得EXP。既存 profile/historyKey 層にフック可能な設計だけ用意)
- **運営プリセット入稿の管理UI**(需要実証前。MVP は手編集 JSON をリポジトリにコミット)

## 2. 統合契約(**最重要・別プロジェクト開発の絶対条件**)

> TM を「別で作って後でくっつける」を成立させるための不変条件。これを外すと統合が苦行になり、仕様書の将来ゴール(キャラ割当・Dashboard・EXP連携)が死ぬ。

| # | 契約 | 根拠 | 破ると起きること |
|---|------|------|------------------|
| C-1 | **最終配置は必ず同一オリジン** `lulumi-tools.com/tasks`(サブパス)。サブドメイン・別ドメイン・外部ホスト(vercel.app 等)を**最終形にしない**(試作の置き場は自由) | LULU-041 | localStorage はオリジン単位。別オリジンだと既存 `maplen-board-*`(マイキャラ/profile)を読めず、キャラ割当・Dashboard・EXP連携が全滅 |
| C-2 | **localStorage 命名は `maplen-board-tasks-v1`**(既存 `maplen-board-*` 系に合わせる) | LULU-008 | 既存 favorites/groups/profile との名前空間整合が崩れる |
| C-3 | **キャラの割当キーは historyKey**(assetKey ベース)。`character.name` をキーにしない | LULU-005 | 改名でキャラ割当が消失。将来 EXP連携時に全面書き直し |
| C-4 | **進捗・リセット残時間・イベント期限の算出は純粋関数**(`taskUtils.js` 等・副作用なし・入力=状態+現在時刻) | 既存 `rankingUtils.js` 方式 | Dashboard が TM 内部に手を突っ込むことになり、統合時に密結合 |
| C-5 | **ルーティングは同一オリジンのハッシュルート `#/tasks`**(OG/SEO 不要な実用ページ) | LULU-052(ハッシュはOG不可だが本ページは流入用でない) | パスルーティング化=全面改修(T6 として一度ドロップ済み)を誘発 |
| C-6 | **UI文言は最初から i18n 前提**(キー化。本体統合時に ja/en/es/th/vi/zh-TW の**6ロケール同時**追加) | LULU-007 | 翻訳穴。プリセット名/イベント名(=データ)の多言語化方針も §3 で決める |
| C-7 | **スタック互換を推奨**: React 19 + Vite + Tailwind(本体と同一) | 統合摩擦の最小化 | 別フレームワーク(Next 等)だと bundler/router の縫い目が増える |

**避けるべき唯一の罠**: 参照サイトのように**別オリジンにデプロイしたアプリを"最終形"にして後から繋ごうとする**こと。試作として別オリジン/ローカルで作るのは全く問題ない。

## 3. データモデル設計(拡張性が本命 — Discord/Dashboard/EXP を後付けしやすく)

### 正(source of truth)の所在 — **正を2箇所に住まわせない**
| データ | 正の所在 | 備考 |
|--------|----------|------|
| 運営プリセット定義(Daily/Weekly/Event の内容・イベント期間) | **静的 JSON(配信物)** | 運営が更新。ユーザーは書き換えない |
| ユーザーのカスタマイズ(有効化/非表示/並び/通知フラグ/キャラ割当/独自タスク/完了状態) | **localStorage `maplen-board-tasks-v1`** | プリセット定義に対する**オーバーレイ**。定義と状態を分離し、**マージは読み取り時の純粋関数1経路に畳む**(同期面を増やさない) |
| キャラ | 既存 `maplen-board-*` profile(historyKey) | TM は**読むだけ**(C-3) |

### スキーマ原則
- **`schemaVersion` を付ける**(生成物・保存物とも)。localStorage は不一致時に前方互換マイグレーション(「書いた本人が読めるか」を設計時に検査)。
- プリセット JSON も `version`(内容フィンガープリント)を持ち、更新検知。
- **通知フラグを最初から器として持つ**(Discord は後付けだが、per-task `notify: bool` と通知対象種別を MVP のデータ構造に入れておく=後付けが移植で済む)。
- 完了状態は**リセット周期でキー化**(例: Daily は `YYYY-MM-DD`、Weekly は ISO 週、Event は eventId 内)。リセット跨ぎで自動的に「未完了」に戻る設計。

### 未確定の外部データ(**要確定・"はず"で作らない**)
- **【要確定】MapleStory N のリセット時刻とタイムゾーン**(Daily/Weekly/Monthly のサーバー基準リセット時刻)。カウントダウンが実ゲームとズレると「約束と請求の不一致」。→ **開発着手前にユーザー/公式で確定**。当面は設定値を1箇所(定数)に集約し差し替え可能に。
- **【要決定】プリセット/イベント名の多言語化**: JSON 内に per-locale フィールドを持つか、キー参照にするか(C-6 と連動)。

## 4. 変わってよいもの・いけないもの

- **変わってよい**: TM の UI/レイアウト・タスク種別内の細部・プリセット JSON スキーマ(schemaVersion で管理する限り)。
- **変わってはいけない(統合の前提)**: §2 の統合契約 C-1〜C-7。既存 `maplen-board-*` localStorage(favorites/groups/profile)への**破壊的変更ゼロ**(TM は自分の名前空間 `maplen-board-tasks-v1` のみ書き、既存キーは読むだけ)。

## 5. 受け入れ基準(数値で)

> TM 本体(別プロジェクト)の受け入れは、参照UIと仕様書 §MVPのゴールに対してユーザーが判断。以下は**統合可能性**に効く機械検証寄りの基準。本体の細目はユーザーが別途定義。

| # | 基準 | 目標値 | 測定方法 |
|---|------|--------|----------|
| 1 | ビルド成功 | 成功 | `npm run build`(TM プロジェクト側) |
| 2 | localStorage 名前空間 | 書き込みキーが `maplen-board-tasks-*` のみ | DevTools Application で確認/コード grep |
| 3 | キャラ割当キー | historyKey ベース(name 非依存) | コード確認・改名シナリオでデータ保持 |
| 4 | リセット跨ぎ | Daily/Weekly 完了が周期境界で未完了に戻る | 時計を進めた再現テスト |
| 5 | バックアップ/復元 | エクスポート→クリア→インポートで状態完全復元 | 手動 or テスト |
| 6 | プリセット定義とユーザー状態の分離 | プリセット JSON 差し替えでユーザーのカスタマイズが保持される | マージ関数の単体テスト |
| 7 | 進捗算出の純粋性 | progress selector が副作用なし・同入力同出力 | 単体テスト |

「見やすくする」は基準ではない。UI 品質はユーザー判断だが、上記は移植成立の必要条件。

## 6. 停止条件

以下に該当したら**開発を止めてユーザーへ選択肢+推奨付きで報告**:
- 統合契約 C-1〜C-7 のいずれかを満たせない設計要求が出た(特に別オリジン必須化の要求)
- リセット時刻(§3 未確定)が確定できず、カウントダウンの正しさを保証できない
- 既存 `maplen-board-*` localStorage を書き換えないと実現できない機能が出た

## 7. 統合方式(代替案比較 → 推奨)

| 案 | 内容 | 利点 | 欠点 | 
|---|------|------|------|
| **A: 別リポ→成果物push(Gear Sim 型, LULU-041)** | 独立 Vite アプリを別リポで開発 → Actions build → 本リポ `/tasks` へ dist push、既存 Pages に相乗り | 主リポから完全隔離。T12b(履歴書換)窓に in-flight ブランチを増やさない | 2つ目の SPA バンドル+deploy 導線。Dashboard 統合は別途 |
| **B(推奨): 試作→本体 `#/tasks` 移植** | ローカル/Vercel 等で自由に試作 → 完成形は `exp_ranking/web` の `#/tasks` ルートへコードを移植 | 同一 App/router/state に自然に入る。統合摩擦が最小。TM は最終的に本体内+Dashboard に溶ける | 試作の学びを移植する一手間 |

**推奨=B**。根拠: TM は「サイト内で開く実用ページ+将来 Dashboard の中核」で、最終的に本体アプリの一部として存在する(architecture-review Step 5「最終アーキテクチャに存在する成果物は前倒しが無駄にならない」)。試作は速度優先で置き場自由、**統合契約 §2 の C-1〜C-7 を守れば移植は機械作業**になる。A も一貫性はあり、ハード隔離を優先するなら可。
