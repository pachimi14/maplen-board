## 0. 背景と裁定

チャートの右端が現在時刻より **4〜8時間前**で止まる。原因は
「進行中の4時間バケットを確定させない」という設計 §9 の規約(途中値が最終値として固定されるのを避けるため)。

**ユーザー裁定**: **進行中バケットを暫定値として描く**。ただし
**破線 + 中抜きマーカー + ツールチップに「暫定」** と明示し、確定値と見分けられるようにする。

**★保存はしない。** 4h テーブルに暫定値を書くと SH-3 受け入れ基準 (a)
「同じ hourly から2回生成したら 4h が完全一致」が壊れ、**決定性を失う**。
∴ **保存物は現状のまま(確定バケットのみ)、API 応答時に暫定点を1つ足す**。

## 2. 現在価格キャッシュ(ユーザー要求)

**要求**: 「リロードの度にユーザーが取得するのではなく、リクエスト時にサーバーが取得し、
全ユーザーがそのキャッシュを最大5分間利用する」

**現状の実装は既にこの形**(`fetch_latest.LatestPriceCache`):
プロセス内・itemId 単位の TTL キャッシュ + **single-flight**(同時アクセスを1リクエストに畳む)。
ブラウザは公式 API を直接叩かない。

∴ **変更は `DEFAULT_TTL_SECONDS = 60.0` → `300.0` の1点のみ**。
環境変数 `SF_HISTORY_LATEST_TTL_SECONDS` で上書きできるようにする(運用で調整可能に)。

## 3. 暫定点の作り方

### 3-1 値の出どころ = `latest` の共有キャッシュ

進行中バケットの値は、**`LatestPriceCache` が持っている現在価格**を使う。理由:

- hourly は4時間ごとのジョブでしか増えないので、それを使うと暫定点も最大4時間古くなり**意味が薄い**
- `latest` は 5分キャッシュで実質リアルタイム。**「現在値」カードと暫定点が同じ数字になる**
  (別々の出どころにすると、同じ画面で2つの「今」が食い違って見える)

### 3-2 応答の形

`prices` の `points` 末尾に、進行中バケットがある場合のみ1点足す:

```json
{ "date": "2026-08-05T00:00:00Z", "prices": [ ... ], "provisional": true }
```

- 確定点には `provisional` を**付けない**(既存の形を壊さない)
- `endDate` は**確定バケットの最後**のまま(暫定点は含めない)。
  代わりに `provisionalDate` を足す(既存フィールドの意味を変えない)

### 3-3 ★上流失敗時は暫定点を出さない(degrade する)

`prices` は現在 **DB 読み出しのみで公式 API に依存していない**。暫定点のために上流依存が入る。
∴ **上流が失敗したら暫定点を省いて確定履歴だけ返す**(200 のまま)。
**`prices` を 503 にしてはいけない** — 履歴が読めなくなるのは明らかな劣化。
(`latest` エンドポイント単体は従来どおり上流失敗で 503。ここは変えない)

### 3-4 統計からは除外する

**期間平均 / 期間高値 / 期間安値 / パーセンタイル は確定点のみで計算する。**
暫定点は値が動くので、含めるとリロードのたびにパーセンタイルが変わり**再現しなくなる**
(設計 §6.1 で「現在値」を統計に混ぜない理由と同じ)。

## 5. 受け入れ基準(数値・機械判定)

- **(a) ★4h テーブルが不変**: 本スライスの前後で `sf_price_history_4h` の
  **行数とハッシュが完全一致**(暫定値が保存されていないことの証明)
- **(b)** `prices` 応答の末尾に `provisional: true` の点が**ちょうど1つ**(進行中バケットがあるとき)。
  無いときは0個
- **(c)** `endDate` は**確定バケットの最後**のまま(暫定点の時刻ではない)
- **(d) ★上流失敗時**: `latest` の取得を失敗させたとき、`prices` が **200 で確定履歴を返し、
  暫定点を含まない**ことをテストで固定
- **(e)** 統計に暫定点が入らないこと: 同じ確定データで暫定点の有無を変えても
  **平均・高値・安値・パーセンタイルが1ビットも変わらない**ことをテストで固定
- **(f)** TTL: `DEFAULT_TTL_SECONDS == 300.0`、環境変数で上書きできることをテストで固定。
  **2回目のアクセスが上流を叩かない**(single-flight と TTL の既存テストを拡張)
- **(g)** `npm run test` 全緑 / `npm run build` 成功 / `pytest` 全緑(**オフライン**)
- **(h)** 6ロケールのキー数が一致(現在 各374 → 追加後も全言語同数)
- **(i)** `git diff -w` で §1 の「触らないもの」に差分ゼロ

## 6. 停止条件

1. **(a) が満たせない**(4h テーブルに書かないと実装できない)→ 設計判断に戻る
2. `prices` が上流依存で遅くなり、**応答の中央値が 500ms を超える**
3. 暫定点を統計から外すと画面が破綻する(除外の前提が成り立たない)
4. §1 の「触らないもの」に触る必要が生じた / 新規依存が必要になった
