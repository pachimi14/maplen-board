# IMPL_PLAN_dq-dup-rows — ranking_snapshot 重複行(identity×日付)のデータ品質修復と再発防止

> 1計画書=1縦切りテーマ(PR-001)。**T12 とは独立したデータ品質バグ修正**。
> 承認者: ユーザー / 実装: implementer / 統括が code-review+実測で検収。
> 発端: T12 P1 調査で発見(重複行調査報告 2026-07-20)。参照 DECISION_LOG(起票予定 LULU-05x)。

## 0. 目的と背景

- **要件を一文で**: `ranking_snapshot` の重複 `(character_asset_key, snapshot_date)` 行が引き起こす**本番 v2 の汚染(偽・負の dailyGain スパイク、履歴チャートの同日二重描画)を止め・既存データを修復し・構造的に再発を防ぐ**。
- **北極星への寄与**: 「毎朝見る」データの**正確性・誠実性**(プロジェクト最優先価値)。現在キャラ個別ページのチャートに実在しない負/巨大スパイクが出ており、信頼を毀損している。
- **実測された実害(調査報告)**: 40 identity・6日(ブートストラップ期 2026-05-29〜06-03)・超過167行。`analysis.py` の (date,identity) 上書きで **dailyGain 105セルが誤り**(例: VeryAlone00 06-02 配信 +6.2B vs 真値 1.4M=約4300倍偽スパイク / Levantine 06-01 配信 −2.36B=あり得ない負値)。**通常の日次取得は原因でない**(06-03以降45日は重複0=再発なし)。原因は初期の再取り込み(復旧再構成・DBマージ)+ `UNIQUE(snapshot_date, rank)` が identity 単位でないこと。

## 2. 三層防御(本計画は下2層 + T12 側1層の全体像で設計)

| 層 | 担当 | 本計画? | 役割 |
|---|---|---|---|
| 復旧側(冪等ガード) | `import_snapshots_from_v2_json`(T12 P1) | 別計画(T12 P1) | 復旧が重複を再生産しない |
| **出力側(防御的集約)** | `analysis.py` | ✅ P-DQ-1 | DB に重複が残っても**出力を汚染させない**(即時・DB無改変) |

## 3. 実装フェーズ(ユーザー指定順・完了は全達成)

- **P-DQ-1(出力側集約・最優先・DB無改変)**: `analysis.py` の `build_analysis_rows` を **`(snapshot_date, identity)` 単位で決定的に1行へ集約**してから progress/dailyGain を計算。採用行=**正行選択規則**(§4)。→ **DB を変えずに現在配信中の v2 汚染(105セル・二重描画)を即時停止**。
- **P-DQ-2(既存データ一回修復)**: 正行選択規則で各 `(snapshot_date, character_asset_key)` 組の1行を残し**超過167行を DELETE**。**dry-run 差分・バックアップ(対象 id と全列値のエクスポート)・対象行一覧・修復前後の v2 ペイロード差分**を必須成果物に。
- **P-DQ-3(DB側再発防止)**: **`UNIQUE(snapshot_date, character_asset_key)` 相当の部分一意制約**(`WHERE character_asset_key != ''`)を追加。**P-DQ-2 の修復後**に制約作成(既存重複が残ると作成失敗するため順序厳守)。

## 4. 正行選択規則・部分一意条件(実データ検証必須・根拠を計画に記載)

**暫定規則(調査で全118組を決定的に解決)**: `class_code/job_code が非空 → fetched_at 最古 → rank 最小`。
- 根拠: 非空 class/job=実取得行の指標(復旧行は必ず空)。fetched_at 最古=リセット直後の最正準。rank は本バグで相違するため単独不可。**exp 単独は不可**(Lvアップで減少し真行識別子にならない)。
- **実装前に実データで再検証し計画/コメントに根拠を残す**エッジケース: ① `character_asset_key` が空/null の行(現状 name-only 重複は0だが将来を想定) ② 改名(name 変化・asset_key 不変) ③ asset_key 欠損 ④ 全行が空 class の組(調査で1組)。
- **部分一意制約の条件**: `WHERE character_asset_key != ''` とし、**空 asset_key の旧 name-only 行を制約対象外に**(既存互換・制約作成失敗回避)。この条件の妥当性(空 asset_key 行に重複がないこと)を実データで確認。

## 5. 変わってよいもの・いけないもの

- **変わってよい**: 該当40キャラ・6日の dailyGain・履歴点(**誤り→正しい値へ**)。DB の重複行(削除)。
- **変わってはいけない**: 重複のない 99.5% のキャラの出力(集約が単一行ケースで恒等)。取得ロジック。v2 形式。latest 日由来の rank/exp/totalExp。

## 6. 受け入れ基準(数値で)

| # | 基準 | 目標値 | 測定方法 |
|---|------|--------|----------|
| 1 | bot テスト | 全緑 | `cd exp_ranking/bot && python -m pytest` |
| 2 | 集約の恒等性(非重複) | 重複のないキャラの出力が集約前後で完全一致 | 実DB由来 fixture 比較 |
| 3 | 汚染セルの是正 | 105セルの dailyGain が corrected 値へ一致・**負の dailyGain 0件**・偽スパイク解消 | 修復前後の v2 ペイロード diff |
| 4 | 履歴点二重化の解消 | 40キャラの同日二重点が単一点に | shard 再生成比較 |
| 5 | 修復後の重複 | `GROUP BY snapshot_date, character_asset_key HAVING COUNT>1` = 0組 | SQL |
| 6 | 制約の実効 | 同一 (date, asset_key) の再挿入が制約で拒否される | 挿入テスト |
| 7 | 修復の可逆性 | バックアップから167行を完全復元できる | dry-run + 復元テスト |

## 7. 停止条件

- 正行選択規則が実データのエッジケース(§4)を決定的に解決できない → 停止・報告(規則の再設計)
- 部分一意制約が既存行(空 asset_key 等)で作成失敗 → 停止・報告(条件見直し)
- 集約が非重複キャラの出力を1件でも変える(恒等性違反)→ 停止・報告
- 取得ロジック(LULU-004)に触れる必要が生じた → 停止・報告
