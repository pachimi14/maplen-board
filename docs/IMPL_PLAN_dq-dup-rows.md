# IMPL_PLAN_dq-dup-rows — ranking_snapshot 重複行(identity×日付)のデータ品質修復と再発防止

> 1計画書=1縦切りテーマ(PR-001)。**T12 とは独立したデータ品質バグ修正**。
> 承認者: ユーザー / 実装: implementer / 統括が code-review+実測で検収。
> 発端: T12 P1 調査で発見(重複行調査報告 2026-07-20)。参照 DECISION_LOG(起票予定 LULU-05x)。

## 0. 目的と背景

- **要件を一文で**: `ranking_snapshot` の重複 `(character_asset_key, snapshot_date)` 行が引き起こす**本番 v2 の汚染(偽・負の dailyGain スパイク、履歴チャートの同日二重描画)を止め・既存データを修復し・構造的に再発を防ぐ**。
- **北極星への寄与**: 「毎朝見る」データの**正確性・誠実性**(プロジェクト最優先価値)。現在キャラ個別ページのチャートに実在しない負/巨大スパイクが出ており、信頼を毀損している。
- **実測された実害(調査報告)**: 40 identity・6日(ブートストラップ期 2026-05-29〜06-03)・超過167行。`analysis.py` の (date,identity) 上書きで **dailyGain 105セルが誤り**(例: VeryAlone00 06-02 配信 +6.2B vs 真値 1.4M=約4300倍偽スパイク / Levantine 06-01 配信 −2.36B=あり得ない負値)。**通常の日次取得は原因でない**(06-03以降45日は重複0=再発なし)。原因は初期の再取り込み(復旧再構成・DBマージ)+ `UNIQUE(snapshot_date, rank)` が identity 単位でないこと。

## 3. 実装フェーズ(ユーザー指定順・完了は全達成)

- **P-DQ-1(出力側集約・最優先・DB無改変)**: `analysis.py` の `build_analysis_rows` を **`(snapshot_date, identity)` 単位で決定的に1行へ集約**してから progress/dailyGain を計算。採用行=**正行選択規則**(§4)。→ **DB を変えずに現在配信中の v2 汚染(重複由来の偽スパイク・二重描画)を即時停止**。
  **責務分離(ユーザー指定)**: P-DQ-1 は**重複行由来の汚染のみ**を担当。**14件の偽スパイク解消＋通常データ(99.48%)不変**を満たせば **P-DQ-1 フェーズ単体は完了扱い可**。P-DQ-1 後に残る負値(実測11セル)は**別原因(単独復元行の精度)= P-DQ-2 の担当**。**データ品質タスク全体は P-DQ-2・P-DQ-3 完了まで閉じない**。
- **P-DQ-2(既存データ一回修復・スコープ拡大)**: 対象2種——(i)正行選択規則で各 `(snapshot_date, character_asset_key)` 組の1行を残し**超過167行を DELETE**、(ii)**ブートストラップ期(2026-05-29〜06-03)の劣化復元行のうち、P-DQ-1 後も負の dailyGain を生む単独行**(実測 11セル)。**dry-run 差分・バックアップ(対象 id と全列値のエクスポート)・対象行一覧・修復前後の v2 ペイロード差分**を必須成果物に。
  **修復前に必須の精密調査(ユーザー指定・実データ)**: ①対象キャラ/日付/現在値 ②負値を作る前後スナップショット ③どの行がブートストラップ復元行か ④正確な EXP を既存DB/git履歴/v1・v2生成物から**回収可能か** ⑤回収不能時、**推測値で埋めず**行削除・欠損扱いにした場合の影響 ⑥11セル修復が weekly/monthly/グラフへ与える差分 ⑦修復対象を**機械的かつ再現可能に特定する条件**。
  **修復方針(データ正確性最優先)**: **回収可能な行は正値へ修復 / 回収不能な行は推測値で埋めず削除または欠損扱いを優先**(過小・過大いずれの推測補完もしない)。**負の dailyGain は原理的にあり得ない**(累積EXPは増加のみ)ため放置しない。
- **P-DQ-3(DB側再発防止)**: **`UNIQUE(snapshot_date, character_asset_key)` 相当の部分一意制約**(`WHERE character_asset_key != ''`)を追加。**P-DQ-2 の修復後**に制約作成(既存重複が残ると作成失敗するため順序厳守)。

## 4. 正行選択規則・部分一意条件(実データ検証必須・根拠を計画に記載)

**確定規則(ユーザー裁定 2026-07-20・実データ全118組で検証済み)**: **`class_code/job_code が非空 → rank 最小`**。
- **`fetched_at` は採用しない**: `SnapshotRow`(`models.py`)にも `load_all_snapshots`(`sqlite_storage.py`)の SELECT にも存在せず `analysis.py` から到達不能。追加は**データモデル変更=事前承認必須**のため**行わない**。
- **`rank 最小` が `fetched_at 最古` の代替として妥当な根拠(実証済み)**: ①全118組で **`rank最小 == fetched_at最古` が一致(不一致0件)**を実DB(`ranking.db.gz`)で確認。②`ranking_snapshot` は **`UNIQUE(snapshot_date, rank)`** を強制するため同一日内で rank は必ず一意=**タイになり得ず常に決定的**。③実データでは復旧再取込み行が常に「class/job空 かつ 数値の大きい rank」に割り当たっており、`class/job非空 → rank最小` が実取得行を正しく選ぶ。
- 補足: class/job非空フィルタのみで 77/118 組が一意、残り41組を `rank最小` で一意化(全て `fetched_at最古` と一致)。全行空 class の1組(BTCaptain/2026-05-31)も `rank最小` で解決。**exp 単独は不可**(Lvアップで減少)。将来の別種破損は P-DQ-3 の制約が構造的に封じるため、出力側規則は既存データの正しい解決で十分。
- エッジケース検証結果(実データ): **改名混入 0組 / 空・null asset_key の重複組 0組**。
- **部分一意制約の条件**: `WHERE character_asset_key != ''` とし、**空 asset_key の旧 name-only 行を制約対象外に**(既存互換・制約作成失敗回避)。空 asset_key 行に重複がないことは確認済み(0組)。

## 5. 変わってよいもの・いけないもの

- **変わってよい**: 該当40キャラ・6日の dailyGain・履歴点(**誤り→正しい値へ**)。DB の重複行(削除)。
- **変わってはいけない**: 重複のない 99.5% のキャラの出力(集約が単一行ケースで恒等)。取得ロジック。v2 形式。latest 日由来の rank/exp/totalExp。

## 7. 停止条件

- 正行選択規則が実データのエッジケース(§4)を決定的に解決できない → 停止・報告(規則の再設計)
- 部分一意制約が既存行(空 asset_key 等)で作成失敗 → 停止・報告(条件見直し)
- 集約が非重複キャラの出力を1件でも変える(恒等性違反)→ 停止・報告
- 取得ロジック(LULU-004)に触れる必要が生じた → 停止・報告
